# Dumb Installer
Dumb Installer installs a project as a system-wide executable by copying it to /opt and generating a wrapper in /usr/local/bin. It’s ideal for small scripts or tools that aren’t worth packaging with setuptools, AUR, or distro packages.
## Installation
```bash
git clone https://github.com/Ben-Collett/dumb_installer
cd dumb_installer/
sudo python dumb_installer.py Ben-Collett/dumb_installer
```

You should now have an executable named din in your path.

## Usage
### Installing project
To run this program you simply run sudo din in the directory of the project you want to install. This project must have a dumb_build.toml

The dumb_build.toml should have a build tag which allows the following options

* **required:** executable_name: defines the name of the executable program. For example in this project you will see `executable_name = "din"` since that is the name of the program installed.
* **required** command: the command to run when the program executes you will likely want to access the path of the project using the `$dumb_project_dir` variable. For example this project uses command = "python $dumb_project_dir/dumb_installer.py"
* excluded: files that will be excluded when creating a copy of this project. Takes a list of strings representing glob patterns. **There is no default** — if you omit it, nothing is excluded, so you will usually want to set it yourself.
* local_install_excluded: additionally excluded when installing from a local directory.
* remote_install_excluded: additionally excluded when installing from a git URL.
* on_install: a command to run after the project is copied into place. Use it to build.
* on_update: a command to run after an update. Use it to rebuild.

The three exclude lists are merged, so a pattern in `excluded` applies in every case.

example dumb_build.toml
```toml
[build]
executable_name = "mytool"
command = "python $dumb_project_dir/main.py"

excluded = [
  "__pycache__",
  "*.pyc"
]
local_install_excluded = [".git"]
remote_install_excluded = []
```

### Uninstalling project
Simply run 
`sudo din -E <program_name>`
to uninstall a program installed through dumb_installer

So to uninstall the dumb installer you run `sudo din -E din`

### Editing PATH on Windows
`--add-to-path` and `--remove-from-path` add or remove the bin directory from your config.toml (`bin_dir`, default `~/.local/bin`) in your user PATH, so installed programs can be run by name.

```bash
din --add-to-path
din --remove-from-path
```

These are Windows only: there the user PATH is the registry value `HKCU\Environment\Path`. Elsewhere the flag exits with an error instead of quietly doing nothing.

To see the options available run `din -h`

## How it works
The current project directory is copied to `/usr/lib/dumb_builds/<executable_name>` when installing system-wide, or `~/.local/lib/dumb_builds/<executable_name>` when installing for the current user. The copy will exclude any files defined by the exclude key in the dumb_build.toml

The wrapper is written to `/usr/local/bin/<executable_name>` (system-wide) or `~/.local/bin/<executable_name>` (per user). Both locations can be overridden in your config.toml.

There is then a wrapper shell file created using the command field at `/usr/local/bin/<executable_name>`

The wrapper file has the following structure
```sh
#!/usr/bin/env sh
dumb_project_dir=<project_dir>
<command> "$@"
```
As an example here is the one generated by building this project

```sh
#!/usr/bin/env sh
dumb_project_dir=/usr/lib/dumb_builds/din
python "$dumb_project_dir/dumb_installer.py" "$@"
```
This is why you will often want to use $dumb_project_dir in your command to access the path of the file you want to execute or call a command on. Because if you don't it will try to run the command in your current working directory 

When uninstalling the dumb_installer simply deletes the dumb_project_dir and the executable file. If there are no files left in the install directory it will be automatically removed until the next time you install a project.

## Testing

```sh
./scripts/test.sh              # the whole suite
./scripts/test.sh -k install   # forwarded to pytest
./scripts/test.sh -m "not sandbox"   # the tests that need no bwrap
```

Tests that touch `/usr/local/bin`, `/usr/lib` or `/etc` run inside a
[bubblewrap](https://github.com/containers/bubblewrap) sandbox, so nothing is
written to your real system. They skip themselves with a clear reason if bwrap
is not installed. See `TESTING_PLAN.md` for the rationale.
